# OpenAPI diff on PR and Bi-directional Contract Testing

This document describes two quality gates complementary to the consumer-driven contract testing (CDCT) already in the repo: the automatic comparison of the OpenAPI spec on every PR, and Bi-directional Contract Testing (BDCT) between the provider spec and the consumer pacts.

## Why compare the OpenAPI spec on every PR

The OpenAPI spec is generated by `@fastify/swagger` from the routes and schemas declared in `src/api/**`. Any change to a route, header, response shape, or status code propagates to `openapi/spec.yaml` when the `scripts/export-openapi.ts` script runs. Without an automatic diff, changes accidentally break clients without leaving a trace in review. The `openapi-diff.yml` workflow makes that impact visible on the PR: it generates the spec for the base ref and the spec for the head ref, compares them, and posts the result as a sticky comment. When it detects a breaking change (e.g., removal of a required field, type change, removal of a status code), the job fails.

## What each tool provides

`oasdiff` operates only on OpenAPI specs. It compares two versions of the same document and classifies each delta as cosmetic (description changed) or breaking (an existing client breaks). It knows nothing about pacts or real traffic. It is fast, deterministic, and runs in a container without project dependencies.

`swagger-mock-validator` works across the two: it takes an OpenAPI spec and a pact JSON and verifies whether each interaction in the pact respects the spec. It answers two questions that the Pact Verifier alone does not: (1) is the consumer expecting something the spec does not promise?; (2) does the spec promise something no consumer exercises? The second question does not fail the build, but it is useful in coverage reviews.

## BDCT vs CDCT

CDCT (consumer-driven) is the current flow in `tests/contract/consumer/` and `tests/contract/provider/`: the consumer writes an expectation against a mock, generates a pact, and the provider replays that pact against the real API. The contract is the pact JSON, and the gate is `can-i-deploy` on the broker.

BDCT (bi-directional) uses two artifacts: the consumer pact (same origin as CDCT) and the provider spec (generated by the provider itself, already validated by functional and schema tests). The broker compares the two and answers whether the spec satisfies the pacts. The advantage is not having to run the Verifier against the real API for each pair; the downside is depending on the spec being reliable. That is why, in this project, BDCT runs as a complementary gate (weekly and on push to main), not as a replacement for CDCT.

Use CDCT when the consumer has subtle business rules (field order, specific enum values, rare headers). Use BDCT when the spec is already the source of truth on the provider and consumers are many, since it avoids N rounds of Verifier against the API.

## How to run the diff locally

Prerequisites: Docker running, branch clean enough to checkout the base (the script stashes automatically if there are changes).

```bash
chmod +x scripts/openapi-diff-local.sh
scripts/openapi-diff-local.sh main
```

The script generates the head spec, stashes, checks out the base, generates the base spec, restores the original branch, and runs two `oasdiff` commands in a container: `diff` (cosmetic) and `breaking` (gate). Output goes to stdout and the exit code reflects the presence of breaking changes.

To compare against another ref, pass it as an argument: `scripts/openapi-diff-local.sh release/1.4`.

## How to read the PR comment

The `openapi-diff` job posts a sticky comment (header `openapi-diff`, updated on every push, no flooding). Structure:

- "Differences" section: everything that changed. Includes additive changes (new routes, new optional fields), which do not block merge.
- "Breaking changes" section: only what breaks clients. If this section lists anything, the job fails.

If the breaking change is intentional (planned deprecation, aligned with consumers), include `[allow-breaking]` in any commit message on the PR. The job reads `git log -1 --pretty=%B` on the PR head and lifts the gate. Use with judgment: BDCT will catch the problem on the next run if no consumer has updated.

## How BDCT publishes the spec to the broker

The `contract-bidirectional.yml` workflow runs on push to main, on a weekly schedule (Monday 08:00 UTC), and on demand via `workflow_dispatch`. When `PACT_BROKER_URL` and `PACT_BROKER_TOKEN` are set as secrets, the job:

1. Generates the OpenAPI spec (`scripts/export-openapi.ts`).
2. Generates the consumer pacts (`npm run test:pact:consumer`).
3. Publishes the pacts to the broker with the `bdct` tag.
4. Publishes the spec as a provider contract, once for each known provider (`UsersAPI`, `OrdersAPI`), with `--content-type=application/yaml`, `--tag=bdct`, and `--provider-app-version` equal to `github.sha`.

When the broker is not configured, the job does not fail because of it: it falls back to local cross-validation using `swagger-mock-validator` per pact/spec pair. This preserves the functional gate even without broker infrastructure on forks or in evaluation environments. The per-pact reports go to `reports/bdct-*.txt` and are available as the `pact-bdct-results` artifact for 30 days.

The original `contract-publish.yml` workflow also gained an optional step to publish the OpenAPI as a provider contract, conditional on the secrets being present. That way, on push to main, the broker simultaneously receives the most recent consumer pact and the most recent provider spec, keeping the compatibility matrix up to date without relying on the weekly workflow run.

## Design decisions

The official image used for oasdiff is `tufin/oasdiff:latest`. It is the public repository maintained by Tufin (the authors of the tool). It runs directly via `docker run`, with no install on the runner. The volume mounted at `/specs` keeps a predictable path for the files.

The breaking change step uses `continue-on-error: false` (default). The cosmetic diff step uses `continue-on-error: true` to avoid masking real problems when the diff fails on noise (e.g., the base spec does not exist yet on the initial PR).

The `[allow-breaking]` bypass is intentionally simple: a grep over the HEAD commit message. No label required, no special review required. The premise is that if the author wrote that, they have already talked to the affected consumers.
